# T03 - Seleccionar la tecnología MPC que utilizará el prototipo

En [T02](https://github.com/CtpN3m01/proyecto-delta/blob/main/T02.md) se investigaron varias tecnologías para trabajar con **Secure Multi-Party Computation (MPC)**:

- MP-SPDZ
- JIFF
- Sharemind MPC
- MPyC

Durante el *daily meeting* se discutieron estas tecnologías y se seleccionaron **MP-SPDZ** y **MPyC** como las dos alternativas principales. Sin embargo, debido a que el proyecto requiere escoger una sola tecnología como base del prototipo, en este documento se realiza una comparación más detallada entre ambas.

El análisis considera principalmente:

- Lenguaje y arquitectura.
- Instalación.
- Deployment.
- Modelos de amenaza (*threat models*).
- Protocolos MPC.
- Seguridad.
- Facilidad de desarrollo.
- Rendimiento y escalabilidad.
- Adecuación para el proyecto.

## 1. Lenguaje y arquitectura

### MPyC

MPyC es un paquete para Python enfocado en realizar cálculos MPC utilizando valores compartidos mediante *secret sharing*. Está implementado principalmente en Python y busca que el desarrollo se mantenga lo más cercano posible a un programa convencional en este lenguaje.

Por ejemplo, MPyC permite trabajar con tipos seguros y operadores sobrecargados para realizar operaciones como suma, multiplicación, comparación, arreglos y otras operaciones sin que el desarrollador tenga que implementar directamente los protocolos criptográficos.

Su arquitectura puede representarse de manera simplificada de la siguiente forma:

```text
Programa Python
      |
      v
     MPyC
      |
      v
Runtime MPC
      |
      +--------+--------+
      |        |        |
      v        v        v
    Party 0  Party 1  Party 2
```

Los participantes se comunican mediante conexiones *peer-to-peer* y el runtime se encarga del intercambio de mensajes necesario para realizar las operaciones sobre los valores secretos.

### MP-SPDZ

MP-SPDZ utiliza un enfoque diferente. Los programas MPC se escriben utilizando un lenguaje de alto nivel basado en Python, pero el programa no se ejecuta directamente como un programa Python tradicional.

El flujo general es:

```text
Programa MPC
    |
    v
Compilador MP-SPDZ
    |
    v
Bytecode
    |
    v
Runtime / Virtual Machine en C++
    |
    +--------+--------+
    |        |        |
    v        v        v
  Party 0  Party 1  Party 2
```

El runtime principal está implementado en **C++**, mientras que Python se utiliza principalmente para definir y compilar los programas MPC.

Esto hace que MP-SPDZ sea más complejo que MPyC, pero también permite optimizaciones más especializadas y la implementación de una gran cantidad de protocolos MPC.

### Comparación

| Característica | MPyC | MP-SPDZ |
|---|---|---|
| Lenguaje de desarrollo | Python | Lenguaje basado en Python |
| Runtime | Python | C++ |
| Compilación previa | No necesariamente | Sí |
| Curva de aprendizaje | Baja-media | Media-alta |
| Cercanía a Python convencional | Alta | Media |
| Flexibilidad criptográfica | Media | Alta |

## 2. Instalación

### MPyC

La instalación de MPyC es sencilla. Actualmente requiere Python 3.10 o superior y puede instalarse utilizando `pip`:

```bash
pip install mpyc
```

MPyC no posee dependencias obligatorias adicionales para su funcionamiento básico.

Opcionalmente se pueden instalar bibliotecas como:

- `numpy`, para operaciones vectorizadas y arreglos seguros.
- `gmpy2`, para mejorar el rendimiento de operaciones con enteros.
- `uvloop`, para mejorar el rendimiento del event loop en sistemas compatibles.

Esto facilita considerablemente la creación de un entorno de desarrollo y pruebas.

### MP-SPDZ

MP-SPDZ requiere un proceso de instalación más complejo debido a que utiliza componentes en C++ y múltiples bibliotecas criptográficas.

Entre sus dependencias se encuentran:

- GCC o Clang.
- GMP.
- libsodium.
- OpenSSL.
- Boost.
- Python.
- Dependencias adicionales según el protocolo seleccionado.

Además, MP-SPDZ debe ser compilado antes de utilizar determinadas máquinas virtuales o protocolos.

Por ejemplo:

```bash
make -j
```

y posteriormente se compila el programa MPC correspondiente.

### Comparación

| Aspecto | MPyC | MP-SPDZ |
|---|---|---|
| Instalación inicial | Muy sencilla | Más compleja |
| `pip install` | Sí | No como método principal |
| Compilación nativa | No | Sí |
| Dependencias externas | Pocas | Varias |
| Tiempo de configuración | Bajo | Mayor |

**Ventaja:** MPyC.

## 3. Deployment

### MPyC

MPyC presenta una gran flexibilidad para deployment debido a que está escrito principalmente en Python.

La documentación indica soporte para:

- Linux.
- Windows.
- macOS.
- Raspberry Pi de 32 bits.
- Arquitecturas de 32 y 64 bits.

Incluso es posible que diferentes participantes utilicen plataformas distintas.

Los participantes pueden configurarse mediante direcciones IP y puertos. MPyC permite utilizar un archivo de configuración o proporcionar directamente la información de cada *party*.

También soporta conexiones SSL mediante la opción:

```bash
--ssl
```

### MP-SPDZ

MP-SPDZ está principalmente orientado a sistemas Linux y arquitecturas x86-64 o ARM64.

Permite ejecutar las diferentes partes en servidores independientes. Cada instancia se identifica mediante un número de participante y establece conexiones con las demás partes del protocolo.

Por ejemplo:

```text
Server A                  Server B                  Server C
Party 0                   Party 1                   Party 2
MP-SPDZ                   MP-SPDZ                   MP-SPDZ
```

MP-SPDZ también permite configurar:

- Hostnames.
- Direcciones IP.
- Puertos.
- Número de participantes.
- Certificados y canales cifrados.
- Servidor externo para facilitar el descubrimiento de participantes.

La documentación indica que los protocolos de mayoría honesta utilizan conexiones SSL cifradas por defecto.

### Comparación

| Aspecto | MPyC | MP-SPDZ |
|---|---|---|
| Linux | Sí | Sí |
| Windows | Sí | Limitado / menos directo |
| macOS | Sí | Sí |
| ARM | Sí | ARM64 |
| Raspberry Pi 32-bit | Sí | No como plataforma principal |
| Ejecución distribuida | Sí | Sí |
| SSL | Sí | Sí |
| Facilidad de deployment | Alta | Media |

Para realizar pruebas rápidamente en equipos heterogéneos, MPyC presenta una ventaja. Para un deployment controlado sobre servidores Linux, ambos son viables.

## 4. Threat Models

El **threat model** define qué comportamiento malicioso o comprometido se asume que puede tener un participante y bajo qué condiciones el protocolo continúa ofreciendo sus garantías de seguridad.

Este punto representa una de las diferencias más importantes entre MPyC y MP-SPDZ.

### MPyC

Los protocolos principales de MPyC se basan en **Shamir Secret Sharing** y están diseñados principalmente para soportar adversarios **pasivos o semi-honestos**.

Un adversario semi-honesto:

1. Puede observar toda la información disponible en el servidor comprometido.
2. Puede intentar obtener información a partir de sus *shares* y mensajes.
3. Sigue correctamente el protocolo MPC.
4. No modifica intencionalmente los mensajes ni el resultado del protocolo.

MPyC utiliza un umbral `t` que debe cumplir:

```text
t < m / 2
```

donde:

- `m` es la cantidad total de participantes.
- `t` es la cantidad máxima de participantes corruptos tolerados.

Por ejemplo, con tres servidores:

```text
Party 0
Party 1
Party 2
```

se puede trabajar con:

```text
t = 1
```

Esto significa que el protocolo protege la privacidad frente a un participante pasivamente comprometido mientras menos de la mitad de las partes estén corruptas.

### MP-SPDZ

MP-SPDZ soporta una variedad mucho mayor de modelos de amenaza.

Entre ellos:

- **Semi-honest / passive adversary**.
- **Malicious / active adversary**.
- **Honest majority**.
- **Dishonest majority**.
- Algunos protocolos con seguridad *covert*.

Un adversario malicioso puede desviarse activamente del protocolo. Por ejemplo, puede intentar:

- Enviar valores incorrectos.
- Modificar *shares*.
- Manipular mensajes.
- Alterar operaciones.
- Producir resultados falsos.

Dependiendo del protocolo seleccionado, MP-SPDZ incorpora mecanismos criptográficos para detectar o resistir este comportamiento.

### Honest majority

Un protocolo de **honest majority** supone que más de la mitad de los participantes permanecen honestos.

Por ejemplo:

```text
3 servidores
     |
     +-- 2 honestos
     |
     +-- máximo 1 corrupto
```

### Dishonest majority

MP-SPDZ también incluye protocolos donde no es necesario asumir una mayoría honesta.

Esto permite modelos donde una gran parte de los participantes podría estar comprometida, dependiendo del protocolo.

Entre los protocolos disponibles se encuentran ejemplos como:

- MASCOT.
- SPDZ2k.
- Rep3.
- Shamir.
- SY/SPDZ-wise.
- BMR.
- Yao.

La posibilidad de escoger entre diferentes modelos de seguridad representa una ventaja considerable para sistemas donde el modelo de amenaza debe definirse explícitamente.

### Comparación de threat models

| Característica | MPyC | MP-SPDZ |
|---|---|---|
| Semi-honest | Sí | Sí |
| Malicious / active | No como modelo principal del runtime | Sí |
| Honest majority | Sí | Sí |
| Dishonest majority | No como enfoque principal | Sí |
| Selección de múltiples protocolos según amenaza | Limitada | Amplia |
| Adecuado para estudiar distintos modelos de seguridad | Media | Muy alta |

**Ventaja:** MP-SPDZ.

## 5. Protocolos MPC

### MPyC

MPyC utiliza principalmente protocolos construidos alrededor de **Shamir's Threshold Secret Sharing**.

Esta decisión simplifica considerablemente la interfaz y permite que el desarrollador trabaje con una abstracción relativamente uniforme.

El framework proporciona tipos seguros para:

- Enteros.
- Punto fijo.
- Campos finitos.
- Arreglos NumPy seguros.
- Comparaciones.
- Operaciones bit a bit.
- Algunas operaciones sobre grupos y polinomios.

### MP-SPDZ

MP-SPDZ fue diseñado precisamente para ejecutar y comparar diferentes protocolos MPC.

Entre los protocolos soportados se encuentran familias basadas en:

- Secret Sharing.
- Replicated Secret Sharing.
- Oblivious Transfer.
- Homomorphic Encryption.
- Garbled Circuits.

La elección del protocolo puede hacerse dependiendo de:

- Cantidad de participantes.
- Modelo de adversario.
- Dominio de cálculo.
- Requerimientos de comunicación.
- Rendimiento esperado.

Por ejemplo, la documentación de MP-SPDZ incluye protocolos para combinaciones como:

| Modelo | Ejemplos |
|---|---|
| Malicious + dishonest majority | MASCOT, SPDZ2k |
| Semi-honest + dishonest majority | Semi, Semi2k |
| Malicious + honest majority | Shamir, Rep3, SY |
| Semi-honest + honest majority | Shamir, ATLAS, Rep3 |

Esta flexibilidad es particularmente importante si durante el desarrollo del proyecto cambia el modelo de amenaza o se desea comparar el rendimiento de distintos protocolos.

**Ventaja:** MP-SPDZ.

## 6. Seguridad

La seguridad de ambos frameworks no debe evaluarse únicamente considerando si utilizan *secret sharing*.

El modelo de seguridad del protocolo seleccionado es igualmente importante.

### MPyC

MPyC proporciona buenas garantías de privacidad bajo su modelo de adversario pasivo.

Sin embargo, si un servidor comprometido puede modificar activamente su comportamiento, el modelo estándar de MPyC no ofrece las mismas garantías que un protocolo diseñado para adversarios maliciosos.

### MP-SPDZ

MP-SPDZ permite seleccionar protocolos diseñados específicamente para adversarios maliciosos.

Esta característica resulta importante para un sistema que eventualmente pueda manejar datos sensibles dentro de un entorno institucional.

Sin embargo, existe una consideración importante: la propia documentación de MP-SPDZ aclara que, aunque sus protocolos se encuentran completamente implementados, esto **no significa que el software completo haya pasado por una auditoría de seguridad equivalente a la requerida para código crítico de producción**.

Por lo tanto, utilizar MP-SPDZ no elimina la necesidad de:

- Revisión de seguridad.
- Pruebas de penetración.
- Auditoría del deployment.
- Gestión segura de certificados y secretos.
- Separación de privilegios.
- Hardening de servidores.
- Monitoreo y logging.
- Revisión del modelo de amenaza.

## 7. Facilidad de desarrollo

### MPyC

MPyC presenta una API cercana a Python.

Esto permite construir rápidamente programas utilizando tipos seguros y operaciones familiares.

Además, cuenta con soporte para arreglos NumPy seguros, lo que puede facilitar operaciones matemáticas y prototipos de procesamiento de datos.

Por esta razón, MPyC resulta especialmente atractivo para:

- Aprendizaje de MPC.
- Prototipos.
- Investigación.
- Validación rápida de algoritmos.
- Aplicaciones donde el modelo semi-honesto sea suficiente.

### MP-SPDZ

MP-SPDZ posee una curva de aprendizaje mayor.

Es necesario comprender conceptos adicionales como:

- Compilación del programa MPC.
- Selección del protocolo.
- Dominio aritmético.
- Preprocesamiento.
- Runtime utilizado.
- Configuración de cada participante.

Sin embargo, esta complejidad permite un control mayor sobre el modelo criptográfico utilizado.

### Comparación

| Aspecto | MPyC | MP-SPDZ |
|---|---|---|
| Facilidad inicial | Alta | Media-baja |
| Similaridad con Python | Alta | Media |
| Complejidad criptográfica visible al desarrollador | Baja | Mayor |
| Cantidad de configuraciones | Baja | Alta |
| Flexibilidad | Media | Muy alta |

**Ventaja en facilidad:** MPyC.  
**Ventaja en control:** MP-SPDZ.

## 8. Rendimiento y escalabilidad

No es correcto afirmar que un framework será siempre más rápido que el otro, ya que el rendimiento MPC depende de múltiples factores:

- Número de participantes.
- Protocolo seleccionado.
- Latencia de la red.
- Ancho de banda.
- Cantidad de multiplicaciones.
- Cantidad de comparaciones.
- Representación numérica.
- Cantidad de rondas de comunicación.

MP-SPDZ está especialmente diseñado para implementar y comparar protocolos MPC y proporciona numerosas optimizaciones y alternativas.

Por ejemplo, su documentación señala que distintos protocolos presentan diferentes ventajas dependiendo del número de participantes y del tipo de operación.

MPyC también incluye optimizaciones, como:

- Operaciones vectorizadas mediante NumPy.
- `gmpy2`.
- Event loops alternativos.
- Evaluación asíncrona.

Sin embargo, dispone de una menor variedad de protocolos para ajustar el sistema a diferentes escenarios de rendimiento y seguridad.
