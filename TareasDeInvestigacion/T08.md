# T08 — Planeamiento de acceso SSH al clúster con WARP y Cloudflare Tunnel

**Estado:** planeamiento; pendiente de ejecutar y validar en el clúster.  
**Fecha:** 17 de septiembre de 2026.

## 1. Objetivo y alcance

Habilitar acceso SSH desde fuera de la red local para trabajar en el clúster y hacer que el acceso vuelva a estar disponible automáticamente cuando se encienda su nodo de acceso. Se aprovechará el SSH existente y se configurará Cloudflare Tunnel como servicio del sistema. El equipo personal utilizará Cloudflare One Client (WARP), registrado en Zero Trust, con permisos de red en Gateway y llaves SSH personales. **Esta variante no requiere comprar ni configurar un dominio propio.**

El repositorio no documenta el sistema operativo ni el administrador del clúster. Este procedimiento propone **Ubuntu/Debian con systemd y permisos sudo**, sobre un nodo de acceso persistente. Si el entorno utiliza otro sistema, adaptar la instalación y los nombres de servicios antes de ejecutar. En un clúster compartido, coordinar estos cambios con su administrador.

La “tarea al encender” será un servicio de systemd. No dependerá de iniciar sesión, abrir una terminal, ejecutar Docker Compose ni enviar un trabajo a Slurm. Si existe Kubernetes, el acceso propuesto se instala en el sistema operativo del nodo; no supone desplegar un servidor SSH dentro de un pod.

## 2. Arquitectura propuesta

```text
Equipo personal fuera de la LAN
  OpenSSH + Cloudflare One Client (WARP), registrado en Zero Trust
          |
          v
Cloudflare Gateway: permite al usuario autorizado acceder por TCP/22
          |
          v
Ruta privada 192.168.0.101/32 -> túnel delta-ssh
          ^ conexión saliente iniciada desde el nodo
          |
Nodo 192.168.0.101: cloudflared -> OpenSSH en 192.168.0.101:22
```

Se usará un túnel administrado desde el panel y una ruta hacia la IP privada. `cloudflared` se instala en el nodo; WARP, en el equipo personal. El cliente debe pertenecer a la misma organización Zero Trust que el túnel. La modalidad elegida es **SSH con llaves administradas por el usuario**, con autorización de red mediante Gateway. [Método oficial](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-device-client/).

La conexión final será `ssh icsj@192.168.0.101`, con WARP conectado desde fuera de la LAN. No se crea un hostname público, registro DNS ni aplicación Access Self-hosted para SSH, y no se usa `ProxyCommand`. OpenSSH sigue autenticando la cuenta Linux con su llave. El registro de dispositivos en Zero Trust es un control separado de las reglas Gateway que autorizan conexiones.

## 3. Datos y requisitos que se deben completar

El acceso SSH local existente, confirmado por el usuario, es:

```bash
ssh icsj@192.168.0.101
```

La guía utiliza esa cuenta y dirección. Falta confirmar si el acceso actual utiliza contraseña o llave. Reemplazar los nombres y correos de ejemplo antes de usarlos. El nombre de organización Zero Trust se elige en Cloudflare; su dirección `NOMBRE_EQUIPO.cloudflareaccess.com` la proporciona Cloudflare y no requiere un dominio propio.

| Dato | Ejemplo utilizado | Valor real |
|---|---|---|
| Nodo de acceso | `delta-acceso` | Pendiente |
| Sistema operativo y versión | Ubuntu/Debian con systemd | Pendiente |
| IP privada del nodo | `192.168.0.101` | `192.168.0.101` (confirmada) |
| Cuenta Linux de trabajo existente | `icsj` | `icsj` (confirmada) |
| Ruta privada del túnel | `192.168.0.101/32` | Un único nodo |
| Nombre de organización Zero Trust | `NOMBRE_EQUIPO` | Pendiente |
| Dominio propio | No necesario | No aplica |
| Nombre del túnel | `delta-ssh` | Pendiente |
| Identidades autorizadas para registro y Gateway | Correos concretos del equipo | Pendiente |
| Equipo personal | Linux, macOS o Windows con OpenSSH | Pendiente |

Antes de comenzar:

- Disponer de acceso local o consola de recuperación y mantener una sesión abierta durante los cambios de SSH.
- Tener una cuenta Cloudflare con capacidad de administrar Tunnel, Zero Trust, dispositivos y Gateway; completar la configuración inicial de Zero Trust.
- Elegir un nodo con almacenamiento persistente, red al arrancar y acceso a los recursos del clúster.
- Comprobar salida hacia los destinos de Cloudflare por **7844 UDP (QUIC) o 7844 TCP (HTTP/2)**, además de DNS y HTTPS para resolución, instalación y autenticación. Permitir ambos transportes facilita la recuperación. Usar la lista oficial de destinos si la red aplica restricciones. [Requisitos de firewall](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/).
- Mantener el puerto 22 inaccesible desde Internet, tanto por IPv4 como por IPv6. Conservar únicamente el acceso LAN que haga falta para administrar el nodo.

## 4. Paso a paso de implementación

### Paso 1 — Confirmar el entorno del nodo

**Dónde:** consola o sesión local del nodo de acceso.

Desde el equipo personal conectado a la LAN, entrar con `ssh icsj@192.168.0.101` y ejecutar los siguientes comandos en esa sesión:

```bash
cat /etc/os-release
ps -p 1 -o comm=
hostname
ip -br address
timedatectl status
```

Confirmar que el proceso 1 es `systemd`, que la hora está sincronizada y que el nodo tiene Internet. Mantener `192.168.0.101` estable mediante reserva DHCP o configuración aprobada de la red; si cambia, habrá que actualizar la ruta, Split Tunnels, las políticas y el cliente SSH.

### Paso 2 — Verificar OpenSSH y preparar las herramientas

**Dónde:** nodo de acceso.

OpenSSH ya permite el acceso local. Conservar su configuración y comprobar su servicio y arranque automático. La instalación siguiente asegura que estén disponibles los paquetes necesarios; no requiere crear otra cuenta ni otro servidor SSH.

```bash
sudo apt-get update
sudo apt-get install -y openssh-server curl ca-certificates tmux
sudo systemctl enable --now ssh.service
sudo systemctl status ssh.service --no-pager
sudo ss -lntp 'sport = :22'
```

Resultado esperado: servicio activo y puerto 22 escuchando, incluyendo una dirección que acepte conexiones a `192.168.0.101`. Si ya existe SSH configurado, conservar sus cuentas y reglas institucionales.

Registrar la huella pública del servidor para compararla en las conexiones siguientes:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

### Paso 3 — Preparar la llave personal y probar SSH en la LAN

**Dónde:** equipo personal. Los ejemplos de shell utilizan Bash, excepto donde se indica Windows.

Si no existe una llave destinada a este acceso, crearla con una frase de paso. No sobrescribir una llave existente:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_delta -C "acceso-delta"
ssh-copy-id -i ~/.ssh/id_ed25519_delta.pub icsj@192.168.0.101
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_delta icsj@192.168.0.101
```

Comparar la huella con la obtenida en la consola antes de aceptar el servidor. Se utilizará la cuenta existente `icsj`. Si ya se accede con otra llave autorizada, se puede conservar y adaptar `IdentityFile` y los comandos a su ruta.

En Windows, crear la llave con OpenSSH usando una ruta como `$env:USERPROFILE/.ssh/id_ed25519_delta`. Si no hay `ssh-copy-id`, copiar **solo el contenido del archivo `.pub`** a `~/.ssh/authorized_keys` de la cuenta del nodo mediante la consola o el acceso local existente, agregándolo sin borrar llaves anteriores. En esa cuenta del nodo:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Comprobar que ambos pertenecen a la cuenta correcta. La llave privada permanece en el equipo personal. Cada persona debe tener su propia cuenta o, como mínimo, su propia llave identificable.

### Paso 4 — Exigir autenticación SSH por llave

**Dónde:** nodo de acceso, después de confirmar el paso 3.

Respaldar la configuración:

```bash
sudo cp -a /etc/ssh /etc/ssh.respaldo-t08-$(date +%Y%m%d-%H%M%S)
sudoedit /etc/ssh/sshd_config
```

Revisar también los archivos incluidos desde `sshd_config.d`. Ajustar estas opciones en el lugar que controle efectivamente la configuración, fuera de bloques `Match` destinados a otros usuarios:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

Si el clúster exige MFA mediante PAM o teclado interactivo, conservar esa política y adaptar este paso con el administrador. OpenSSH suele tomar el primer valor encontrado para una opción; no basta con agregar líneas al final.

```bash
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T
```

Revisar las cuatro opciones en la salida; si hay reglas `Match`, evaluar también la configuración de la cuenta y dirección de conexión con `sshd -T -C`. **Solo si la validación es correcta**, aplicar:

```bash
sudo systemctl reload ssh.service
```

Abrir una segunda conexión LAN con la llave y verificarla antes de cerrar la sesión de recuperación.

### Paso 5 — Instalar cloudflared

**Dónde:** nodo de acceso, en la sesión `root@cluster1`. Estos comandos no llevan `sudo` porque se ejecutan como root. Ejecutarlos uno por uno y continuar solo si el anterior termina sin errores. Utilizar el repositorio estable oficial.

**5.1. Crear el directorio para la clave del repositorio:**

```bash
install -d -m 0755 /usr/share/keyrings
```

**5.2. Descargar la clave del repositorio:**

```bash
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg -o /tmp/cloudflare-main-t08.gpg
```

**5.3. Instalar la clave descargada:**

```bash
install -m 0644 /tmp/cloudflare-main-t08.gpg /usr/share/keyrings/cloudflare-main.gpg
```

**5.4. Agregar el repositorio estable de Cloudflare:**

```bash
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' > /etc/apt/sources.list.d/cloudflared.list
```

**5.5. Actualizar el índice de paquetes:**

```bash
apt-get update
```

**5.6. Instalar cloudflared:**

```bash
apt-get install -y cloudflared
```

**5.7. Comprobar la versión instalada:**

```bash
cloudflared --version
```

Detenerse si falla la descarga o la verificación de APT. [Repositorio oficial de paquetes](https://pkg.cloudflare.com/index.html).

### Paso 6 — Preparar Zero Trust, registro de equipos y permisos

**Dónde:** navegador, panel de Cloudflare. Los nombres de menús pueden variar.

#### 6.1 Organización y registro

1. Crear o seleccionar la organización Zero Trust y anotar su **team name** como `NOMBRE_EQUIPO`.
2. En **Zero Trust → Team & Resources → Devices → Device profiles → Management**, abrir **Device enrollment permissions**.
3. Crear una política de registro que permita únicamente los correos concretos del equipo. No usar `Everyone`.
4. En **Login methods**, seleccionar el proveedor de identidad o habilitar el código de un solo uso por correo. Guardar. Si se exige MFA, usar un proveedor y una política que lo implementen; el código por correo por sí solo no equivale a MFA.

El registro autoriza a incorporar dispositivos; no basta para limitar a qué servidor pueden conectarse. [Permisos de registro](https://developers.cloudflare.com/learning-paths/secure-internet-traffic/configure-device-agent/device-enrollment-permissions/).

#### 6.2 Activar el proxy de red

En **Traffic policies → Traffic settings → Proxy and inspection**, habilitar **Allow Secure Web Gateway to proxy traffic** y **TCP**. Para esta tarea se usará SSH por TCP/22; no se necesita habilitar inspección TLS. [Proxy de Gateway](https://developers.cloudflare.com/learning-paths/replace-vpn/configure-device-agent/enable-proxy/).

#### 6.3 Restringir el acceso al nodo

Antes de crear la ruta privada, abrir **Traffic policies → Firewall policies → Network** y definir estas reglas en el orden indicado:

| Orden | Nombre propuesto | Condiciones | Acción |
|---|---|---|---|
| 1 | `T08 permitir SSH` | Destination IP **is** `192.168.0.101` **AND** Destination Port **is** `22` **AND** Protocol **is** `TCP` **AND** User Email en la lista de correos autorizados | Allow |
| 2 | `T08 bloquear resto del nodo` | Destination IP **is** `192.168.0.101`, sin limitar usuario ni puerto | Block |

Con el operador **is**, introducir la IP sin `/32`; ese operador compara una dirección individual. Mantener `192.168.0.101/32` en la ruta CIDR y en Split Tunnels del paso 8. Agregar el correo en **And identity matches… → User Email**, separado de las condiciones de tráfico. Para un único correo usar **is** con el correo exacto que se utilizará para registrar WARP.

Dentro de la lista de correos se permite cualquiera de los correos indicados; entre las categorías se usa **AND**. Mantener la excepción SSH por encima del bloqueo y revisar que ninguna regla Allow más amplia anterior permita saltarse esta restricción. La segunda regla cubre también otros puertos del nodo.

Gateway no deniega automáticamente todo lo que no coincide con la primera regla: el bloqueo explícito es necesario. En una organización con más redes privadas, integrar estas reglas con su bloqueo general existente sin cambiar accesos ajenos a T08. [Políticas de red](https://developers.cloudflare.com/cloudflare-one/traffic-policies/network-policies/common-policies/) y [diferencia entre Gateway y Access](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/choose-application-type/).

### Paso 7 — Crear el túnel e instalar su servicio

**Dónde:** panel de Cloudflare y nodo de acceso.

1. Ir a **Networking → Tunnels**, crear un túnel de tipo `cloudflared` y asignarle `delta-ssh`.
2. Seleccionar Linux y la arquitectura correspondiente al nodo.
3. Obtener el token del conector mostrado por el panel. Guardarlo como secreto; no incluirlo en este documento, Git ni capturas.
4. Si ya existe un servicio `cloudflared` en el nodo, revisar qué túnel atiende antes de modificarlo. El procedimiento siguiente supone una instalación nueva.
5. En Bash del nodo, instalar el servicio usando el token sin escribir su valor literal en el historial:

```bash
read -r -s -p "Token del túnel: " DELTA_TUNNEL_TOKEN
printf '\n'
sudo cloudflared service install "$DELTA_TUNNEL_TOKEN"
unset DELTA_TUNNEL_TOKEN
sudo systemctl enable --now cloudflared.service
```

El instalador puede guardar el token en la definición del servicio y sus argumentos; tratar esa configuración y cualquier salida que la muestre como material sensible. El uso de `read` evita guardarlo literalmente en el historial, pero no elimina esa persistencia necesaria para arrancar.

Esperar a que el conector aparezca conectado en el panel. El token autentica al conector, no a las personas que entran por SSH. [Instalación oficial del túnel como servicio](https://developers.cloudflare.com/tunnel/get-started/).

### Paso 8 — Crear la ruta privada y configurar Split Tunnels

**Dónde:** panel de Cloudflare.

#### 8.1 Ruta al nodo

En **Networking → Routes → Create route → Tunnel CIDR**, crear:

| Campo | Valor |
|---|---|
| Túnel | `delta-ssh` |
| IP/CIDR | `192.168.0.101/32` |
| Descripción | `T08 SSH nodo de acceso` |
| Red virtual | `default`, si no hay otra definida para este entorno |

La ruta `/32` identifica únicamente este nodo. No agregar toda `192.168.0.0/24` para esta tarea. Si ya existe una ruta idéntica en otro túnel, resolver el conflicto antes de continuar. [Creación de rutas privadas](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/cloudflared/connect-cidr/).

Desde el nodo donde corre `cloudflared`, comprobar que OpenSSH acepta la IP de destino:

```bash
ssh icsj@192.168.0.101
```

Esta comprobación puede pedir las credenciales locales existentes; no copiar la llave privada personal al servidor para realizarla. Si no se dispone de credenciales allí, confirmar el listener con `ss` y revisar el firewall local. No se debe limitar SSH a `127.0.0.1`, porque el destino de esta ruta es `192.168.0.101`.

#### 8.2 Perfil WARP y Split Tunnels

1. En **Team & Resources → Devices → Device profiles → General profiles**, crear o editar el perfil que se asignará al equipo de T08. Comprobar su regla de asignación y prioridad; conservar otros perfiles existentes.
2. Usar modo **Traffic and DNS** —también llamado Gateway with WARP— para transportar tráfico de red.
3. Respaldar las entradas actuales de Split Tunnels. Seleccionar **Include IPs and domains**.
4. Incluir `192.168.0.101/32`, el dominio real `NOMBRE_EQUIPO.cloudflareaccess.com` y los dominios del proveedor de identidad utilizado para autenticarse. Añadir los otros destinos de Zero Trust que requieran las funciones habilitadas, siguiendo la referencia oficial.
5. Guardar y comprobar después, en el cliente, que recibió el perfil.

Include envía por WARP los destinos incluidos; no obliga a enviar toda la navegación por el túnel. El DNS tiene su propia configuración y puede seguir usando Gateway. No basta con crear la ruta del servidor: la IP también debe entrar en WARP desde el cliente. [Split Tunnels y destinos necesarios](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/route-traffic/split-tunnels/).

Para la primera prueba, usar una red externa que no se solape con `192.168.0.0/24`. Si la red de casa usa el mismo rango, puede haber conflicto, especialmente si la computadora o su gateway tienen `192.168.0.101`. Probar desde otra red y resolver el direccionamiento con el administrador; una red virtual de Cloudflare no corrige por sí sola una colisión en la LAN del cliente. No cambiar la IP del clúster durante una sesión remota sin acceso de recuperación.

### Paso 9 — Configurar el arranque y la recuperación automática

**Dónde:** nodo de acceso.

Habilitar ambos servicios y añadir una configuración complementaria para el túnel:

```bash
sudo systemctl enable ssh.service cloudflared.service
sudo systemctl edit cloudflared.service
```

Agregar en el área editable del archivo:

```ini
[Unit]
Wants=network-online.target
After=network-online.target
StartLimitIntervalSec=0

[Service]
Restart=always
RestartSec=10s
```

Aplicar mientras todavía se dispone de acceso local, porque reiniciar el túnel interrumpe sus conexiones:

```bash
sudo systemctl daemon-reload
sudo systemctl restart cloudflared.service
sudo systemctl is-enabled ssh.service cloudflared.service
sudo systemctl is-active ssh.service cloudflared.service
sudo systemctl show cloudflared.service -p Restart -p RestartUSec -p After -p Wants
```

Se espera `enabled` y `active` para ambos. `Restart=always` recupera el proceso si termina; un `systemctl stop` intencional lo mantiene detenido. La propia conexión del túnel reintenta ante pérdidas de red. `network-online.target` ordena el arranque, pero no garantiza que Internet ya esté disponible; por eso también se deben probar los reintentos.

Si el nodo utiliza `ssh.socket`, revisar también su estado y la configuración de activación por socket de la distribución; no deshabilitarla a ciegas. Lo que debe verificarse es que SSH acepte conexiones tras arrancar, antes de cualquier inicio de sesión local.

### Paso 10 — Instalar y registrar WARP en el equipo personal

**Dónde:** equipo personal, con permisos para instalar software.

1. Instalar **Cloudflare One Client (WARP)** para el sistema operativo desde las [descargas oficiales](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/downloads/).
2. Abrir sus preferencias de cuenta y elegir **Login with Cloudflare Zero Trust**. Introducir el team name real `NOMBRE_EQUIPO` y completar la autenticación.
3. Confirmar en el cliente la organización correcta y, en el panel, que aparece el equipo registrado con la identidad esperada y el perfil de T08.
4. Conectar WARP y comprobar que usa **Traffic and DNS**. El modo DNS-only no transporta SSH; activar WARP como consumidor sin registrarse en la organización tampoco da acceso a este túnel.

En Linux, después de instalar el paquete oficial, se puede registrar desde la terminal del usuario, sin `sudo`. Ejecutar el primer comando con el nombre real del equipo y completar el navegador antes de continuar:

```bash
warp-cli registration new NOMBRE_EQUIPO
warp-cli registration show
warp-cli connect
warp-cli status
```

Si ya pertenece a otra organización, no borrar su registro sin revisar esa configuración. [Instalación y registro manual](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/manual-deployment/).

Para conservar el comando habitual con la llave creada en el paso 3, agregar estas entradas a `~/.ssh/config` —en Windows, `%USERPROFILE%\.ssh\config`— sin duplicar ni sobrescribir configuraciones anteriores:

```sshconfig
Host delta-cluster 192.168.0.101
    HostName 192.168.0.101
    User icsj
    IdentityFile ~/.ssh/id_ed25519_delta
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
    ForwardAgent no
```

Si se conserva una llave anterior, sustituir `IdentityFile` por su ruta. Retirar de esta entrada cualquier `ProxyCommand` del planteamiento anterior. Con WARP conectado, ambos comandos deben acceder al mismo nodo:

```bash
ssh icsj@192.168.0.101
ssh delta-cluster
```

Comparar la huella del servidor con la registrada en el paso 2. No se instala `cloudflared` ni el token del túnel en el equipo personal. La autenticación Zero Trust sucede al registrar o reautenticar WARP; OpenSSH mantiene su autenticación independiente.

### Paso 11 — Validar desde fuera de la red local

Conectar el equipo personal a otra red sin solapamiento de direcciones, por ejemplo un punto de acceso del teléfono. Confirmar que WARP está conectado a la organización y ejecutar:

```bash
ssh delta-cluster
hostname
whoami
```

Los dos últimos comandos se ejecutan dentro de la sesión remota. Deben identificar al nodo y a la cuenta esperados. Realizar además estas pruebas desde esa red externa:

- Desconectar WARP e intentar abrir una nueva conexión: no debe alcanzar el nodo del clúster. Volver a conectar WARP.
- Intentar registrar una identidad fuera de la política de inscripción: debe ser rechazada.
- Para comprobar Gateway con la propia cuenta autorizada, retirar temporalmente su correo de la regla `T08 permitir SSH`, manteniendo el bloqueo, y abrir una nueva conexión: debe quedar denegada. Conservar acceso al panel y a la consola para restaurar el correo y repetir la prueba positiva. Si existe una identidad de prueba ya inscrita sin permiso SSH, se puede usar en su lugar.
- Revisar en los registros de red Gateway la IP destino, identidad, acción y regla aplicadas. Registrar las denegaciones; no confundir un rechazo de llave SSH con un bloqueo de Gateway.

No usar `ping` como criterio de aceptación: esta guía autoriza TCP/22 y no configura ICMP.

Para copiar archivos desde el equipo personal:

```bash
scp ./archivo.txt delta-cluster:~/
```

Para trabajar con procesos interactivos que sobrevivan a una desconexión, dentro del nodo:

```bash
tmux new -As delta
```

Desacoplar con `Ctrl+B`, luego `D`, y volver con el mismo comando. `tmux` no conserva procesos tras apagar o reiniciar el nodo. Los cómputos del clúster deben ejecutarse mediante su gestor de trabajos si existe; el nodo de acceso sirve para entrar y administrarlos.

Si se necesita entrar a otro nodo, configurar su cuenta y llave autorizadas por separado. Desde el cliente se puede usar `ssh -J delta-cluster usuario_nodo@IP_PRIVADA_NODO` cuando la política SSH del nodo de acceso permite ese salto. No copiar la llave privada al clúster ni habilitar agent forwarding para conseguirlo.

### Paso 12 — Comprobar el encendido automático

Realizar esta prueba en una ventana sin trabajos afectados y con consola de recuperación disponible:

1. Registrar una conexión externa exitosa del paso 11.
2. Reiniciar **solo el nodo de acceso** con `sudo reboot`.
3. Esperar a que vuelva su red y ejecutar `ssh delta-cluster` desde el equipo personal con WARP conectado, sin iniciar sesión local en el nodo ni lanzar servicios manualmente.
4. Ya dentro del nodo, verificar:

```bash
systemctl is-enabled ssh.service cloudflared.service
systemctl is-active ssh.service cloudflared.service
sudo journalctl -u cloudflared.service -b --no-pager -n 50
sudo journalctl -u ssh.service -b --no-pager -n 50
```

5. En una prueba posterior de apagado y encendido del clúster, comprobar que el nodo de acceso y los equipos de red también arrancan. Si es una VM, configurar su autoinicio en el hipervisor; si es físico, revisar el comportamiento de encendido tras recuperar energía.
6. Con acceso local disponible, probar una interrupción breve de Internet. Al restablecer la red debe poder abrirse una **nueva** conexión SSH sin lanzar `cloudflared` manualmente; la sesión anterior puede haberse perdido.

## 5. Operación y resolución de problemas

Consultar los registros localmente y ocultar tokens o información sensible antes de adjuntar evidencias:

```bash
sudo journalctl -u cloudflared.service --since "15 minutes ago" --no-pager
sudo journalctl -u ssh.service --since "15 minutes ago" --no-pager
```

| Síntoma | Comprobación y acción |
|---|---|
| Túnel desconectado | Revisar energía, red, DNS, servicio, token y salida 7844 TCP/UDP. |
| Túnel conectado, pero SSH falla | Revisar ruta `/32`, red virtual, perfil Include aplicado, proxy TCP, políticas Gateway y listener `192.168.0.101:22`. |
| Registro WARP rechazado | Revisar team name, correo, proveedor y política de inscripción. |
| WARP conectado, pero Gateway deniega | Revisar identidad registrada, orden y condiciones de reglas y registros de red. |
| `Permission denied (publickey)` | Revisar cuenta Linux, `IdentityFile`, llave pública autorizada, propietario y permisos. |
| Se llega a otro equipo o hay conflicto de IP | Revisar solapamiento con la LAN del cliente; probar desde otra red y verificar siempre la huella SSH. |
| Funciona hasta reiniciar | Revisar habilitación de servicios, registros del arranque, persistencia del token y autoinicio de red/VM. |
| Cambia la huella SSH | Verificar la causa desde la consola; no borrar `known_hosts` ni aceptar la nueva huella sin comprobarla. |
| Sesiones largas se cortan | Revisar red, vigencia del registro/sesión WARP y registros; reconectar y recuperar `tmux`. |

Esta modalidad usa conectividad privada a través de WARP. Los keepalives ayudan a detectar cortes, pero no garantizan una sesión indefinida. El arranque del túnel en el clúster es automático; el equipo personal debe tener WARP conectado y una autenticación vigente para acceder. Se puede configurar conexión automática en su perfil, pero una reautenticación requerida seguirá necesitando intervención.

Actualizar OpenSSH y `cloudflared` mediante APT en ventanas de mantenimiento y mantener actualizado WARP. Repetir una prueba externa tras cambios. Al retirar a una persona, eliminar su autorización Gateway y de registro, revocar sus dispositivos/sesiones y retirar su cuenta o llave SSH. Si se filtra el token del túnel, rotarlo en Cloudflare y actualizar el conector mediante el procedimiento del panel.

## 6. Recuperación o reversión

- Si falla un cambio de SSH, usar la sesión local conservada o la consola, restaurar los archivos modificados desde el respaldo, ejecutar `sshd -t` y recargar `ssh.service` solo si valida.
- Para desactivar este acceso externo, desde la consola ejecutar `sudo systemctl disable --now cloudflared.service` y retirar la ruta privada `192.168.0.101/32` asociada a este túnel. Mantener el bloqueo Gateway hasta retirar la ruta y luego revertir únicamente las reglas y el perfil creados para T08.
- Conservar el acceso SSH local autorizado para corregir el problema. Detener el túnel no requiere desinstalar OpenSSH.
- Si el nodo alojaba otros túneles o servicios antes de T08, revertir únicamente los cambios de esta tarea.
