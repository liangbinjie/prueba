# T09 — Entrada segura, Secret Sharing y distribución a parties

## Objetivo

Implementar la primera entrada segura de Proyecto Delta: registrar un trabajo, preprocesar un MP4 en el equipo confiable del usuario, producir tres secret shares provisionales, entregarlos directamente a tres mock parties y coordinar el estado sin exponer el video al servidor central.

## Problema de seguridad

Enviar el MP4 original a un servidor central concentraría toda la información sensible en un único punto. Una filtración, error de acceso o compromiso del servidor revelaría rostros, placas y contexto de videovigilancia. Por ello el original solo se abre en el cliente local; no se carga al Coordinator ni a ninguna party. Cada party recibe únicamente un share que, de forma individual, no representa directamente el contenido.

## Arquitectura: Control Plane y Data Plane

El **Control Plane** es el Coordinator FastAPI. Registra metadata (`filename` y `format`), crea el UUID, publica las URLs de las parties, recibe confirmaciones sin contenido secreto y calcula el estado del trabajo.

El **Data Plane** conecta directamente el cliente con las parties. El Coordinator nunca recibe ni reenvía shares.

```text
                         metadata/estado
Cliente confiable <--------------------------> Coordinator :8000
       |
       | MP4 (solo local)
       v
VideoPreprocessor -> payload binario -> ShareGenerator
                                      /      |      \
                                    S0       S1       S2
                                     |        |        |
                                     v        v        v
                               Party 0   Party 1   Party 2
                                :8100     :8101     :8102
                                     \        |        /
                                      confirmaciones
                                            |
                                            v
                                      Coordinator
```

## Componentes

### Coordinator

Mantiene los trabajos en memoria. Al registrar un MP4 genera un UUID4 y establece `WAITING_FOR_SHARES`, con las parties 0, 1 y 2 en `PENDING`. Cada confirmación válida cambia una party a `RECEIVED`; solamente cuando las tres confirmaron el estado pasa a `READY_FOR_MPC`. Reiniciar el contenedor elimina estos estados, una limitación aceptada para T09.

### Mock Parties

Los tres contenedores ejecutan exactamente la misma aplicación `party_receiver`. `PARTY_ID` determina su identidad. Cada instancia acepta bytes, valida el UUID y el tipo de contenido, guarda únicamente su propio `<video_id>.share` mediante `LocalStorage` y notifica al Coordinator usando su URL interna de Docker. Nunca interpreta ni reconstruye el secreto.

### Cliente CLI

`python -m client upload <video.mp4>` se ejecuta fuera de Docker. Valida ruta y extensión, registra metadata, procesa el archivo en local, genera tres shares, envía `S0` a P0, `S1` a P1 y `S2` a P2, y consulta el estado final. Los errores de conexión o de una party producen una salida clara y un código no exitoso.

### Preprocesamiento local

OpenCV decodifica todos los frames como arrays NumPy. Para evitar acumular el video completo sin comprimir en RAM, cada frame se codifica inmediatamente como JPEG con calidad 90 y se agrega a un contenedor binario con longitud prefijada. El contenedor incluye número de frames, dimensiones, canales, FPS, `dtype`, versión y codificación. El MP4 original no se copia ni se guarda en servicios remotos.

### Secret Sharing provisional

`ShareGenerator` delimita la responsabilidad para poder sustituir el algoritmo sin cambiar la CLI, el Coordinator ni la capa de red. La implementación de T09 opera sobre cada byte del payload `D`:

```text
S0 = bytes aleatorios
S1 = bytes aleatorios
S2 = D XOR S0 XOR S1
D  = S0 XOR S1 XOR S2
```

Los bytes aleatorios provienen de un generador criptográficamente seguro. Los tres shares cubren el mismo secreto; no son fragmentos o grupos distintos de frames.

> **PROTOTIPO DE T09:** este esquema XOR no es el formato definitivo ni afirma compatibilidad con MP-SPDZ. Se usa para demostrar el flujo seguro y será reemplazado por un adaptador de entrada compatible con el protocolo MPC elegido.

## Endpoints

| Servicio | Método y ruta | Contenido |
|---|---|---|
| Coordinator | `POST /api/v1/videos` | JSON con `filename` y `format`; devuelve UUID, estado y parties |
| Coordinator | `GET /api/v1/videos/{video_id}` | Estado general e individual por party |
| Coordinator | `POST /api/v1/videos/{video_id}/confirmations` | JSON de confirmación con `party_id` y `status`; nunca incluye el share |
| Party | `POST /api/v1/shares/{video_id}` | Share como `application/octet-stream` |

## Variables de entorno

| Variable | Consumidor | Propósito |
|---|---|---|
| `COORDINATOR_URL` | CLI | URL pública, por defecto `http://localhost:8000` |
| `PARTY_URLS` | Coordinator | Tres URLs públicas separadas por comas |
| `COORDINATOR_INTERNAL_URL` | Parties | DNS interno `http://coordinator-api:8000` |
| `PARTY_ID` | Party | Identidad 0, 1 o 2 |
| `PARTY_STORAGE_DIR` | Party | Directorio donde esa instancia guarda sus shares |

`.env.example` contiene valores de referencia sin secretos. La distinción entre URL pública e interna evita que una party intente contactar su propio contenedor mediante `localhost`.

## Docker y ejecución

Desde la raíz del repositorio:

```bash
docker compose up --build
```

En otra terminal se instala y ejecuta el cliente local:

```bash
python -m venv .venv
# Activar .venv según el sistema operativo
python -m pip install -r requirements.txt
python -m pip install -e .
python -m client upload ./video.mp4
```

## Comprobación manual esperada

La CLI debe finalizar con `Estado: READY_FOR_MPC`. El UUID mostrado permite consultar:

```text
GET http://localhost:8000/api/v1/videos/<video_id>
```

Deben existir exactamente los archivos correspondientes en:

```text
data/parties/party-0/<video_id>.share
data/parties/party-1/<video_id>.share
data/parties/party-2/<video_id>.share
```

No debe aparecer el MP4 original dentro del almacenamiento del Coordinator ni de las parties. Con una o dos confirmaciones el estado debe permanecer `WAITING_FOR_SHARES`; con las tres debe ser `READY_FOR_MPC`.

## Criterios de aceptación

- Docker Compose define Coordinator en `:8000` y tres instancias del mismo receptor en `:8100`, `:8101` y `:8102`.
- La CLI valida archivo y extensión MP4 y todo el preprocesamiento sucede localmente.
- El Coordinator recibe solo metadata/confirmaciones y genera el UUID4.
- Se crea una representación binaria y tres shares matemáticos del mismo payload.
- Cada share viaja directamente y exclusivamente a su party correspondiente.
- Cada party guarda un solo archivo por trabajo y confirma sin transmitir su contenido.
- El estado refleja correctamente confirmaciones parciales y completas.
- El generador provisional está separado de networking y puede reemplazarse.

## Limitaciones actuales y trabajo futuro

T09 no ofrece persistencia del Coordinator, autenticación, TLS, reintentos automáticos ni límites avanzados de carga. Aunque los frames se decodifican y codifican uno por uno, el payload binario y los tres shares todavía se materializan completos en memoria; no existe streaming HTTP integral para videos arbitrariamente grandes. El esquema XOR exige los tres shares y no sustituye un protocolo MPC de producción. Tampoco hay todavía detección de rostros/placas, anonimización o reconstrucción del video.

La representación JPEG de T09 usa compresión con pérdida: conserva todos los frames y sus dimensiones, pero no garantiza igualdad píxel a píxel con los arrays decodificados originalmente. Es una decisión provisional para mantener viable el flujo completo con videos reales mientras se define el formato de entrada de MPC.

El siguiente paso será reemplazar el generador provisional por una entrada compatible con MP-SPDZ y conectar el receptor HTTP a un adaptador de party MPC, conservando el contrato de la CLI, el Control Plane y la distribución directa. Después podrán incorporarse Computer Vision y anonimización sobre el procesamiento seguro definido por el proyecto.
